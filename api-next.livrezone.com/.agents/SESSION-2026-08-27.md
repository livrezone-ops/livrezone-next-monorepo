## 4. 🔍 Incident « tous les sites en 403 » — RÉSOLU
Symptôme : tous les sites de `/workspace` renvoyaient 403 **uniquement dans le navigateur
de l'administrateur** (le reste du monde accédait normalement — vérifié par curl externes → 200,
y compris pages lisant la base).

**Cause racine (prouvée par les logs Caddy)** :
> Le WAF **Coraza** (OWASP CRS 4.x intégré à Caddy/OpenPanel) bloquait toute requête portant
> le **cookie PostHog** (`ph_phc_…posthog`), car ce cookie contient la chaîne **`.vscode`**
> → règle **930120** « OS File Access Attempt » → score d'anomalie 5 → règle **949110** → 403.
> Les IP clientes vues étaient des IP Cloudflare (trafic proxifié).

- Aucun lien avec les permissions ou les modifications de la session (innocentées).
- **Contournement immédiat** : navigation privée ou effacement du cookie `ph_phc*` pour `*.livrezone.com`.
- **Correctif permanent à faire** : exclusion CRS ciblée via
  `/etc/openpanel/caddy/coreruleset/rules/REQUEST-900-EXCLUSION-RULES-BEFORE-CRS.conf`
  (exclusion du cookie `ph_phc_.*posthog` pour les règles 930120/930130), puis reload Caddy.

**Diagnostics annexes (sans rapport avec la session)** :
- `dev.livrezone.com` → 500 préexistants (23–26 août) : `REDIS_HOST=livrezone-redis` inexistant,
  `SESSION_DRIVER=redis` ⇒ chaque requête meurt. Conteneur redis absent de `docker ps -a`.
- `fastfacture.livrezone.com` → 500 préexistants : `DB_HOST=mariadb` inexistant.
- Caddy tente en boucle (~7 jours) d'émettre des certificats ACME staging pour
  `example.net` / `webmail.example.net` (débris de config, non bloquant).
