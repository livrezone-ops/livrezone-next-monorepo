# AUDIT TECHNIQUE COMPLET — LivreZone — 06/09/2026

Périmètre : backend `api-next.livrezone.com` (Laravel 13.24, PHP 8.5, Sanctum, Scout/Meilisearch, Redis, MariaDB) + frontend `next.livrezone.com/frontend` (Next.js 16.3, React 19.2, TanStack Query 5).
Méthode : revue statique du code réel (134 fichiers PHP backend, ~26 900 lignes TS/TSX frontend, 49 migrations, 92 tests), croisement avec la roadmap et les audits des 25/08, 30/08 et 31/08. Aucun secret affiché. Chaque constat cite le fichier concerné.

> Delta vs audit 31/08 : les chantiers annoncés sont bien livrés (22 Form Requests, fusion ListingManagerController, throttle:auth, Policies chat/listing, app:queue-health, flock sur les crons, CI verte, backup Drive + test de restauration, secret Telegram hash_equals). Ce rapport identifie ce qui reste ET les nouveaux problèmes introduits depuis (déploiement, env, CI, index Meili désynchronisé).

Front : 15 références de domaine restantes sur 12 fichiers (en baisse vs ~39) : `lib/books-api.ts`, `lib/axios.ts`, `app/page.tsx`… → centraliser.
- **Code mort identifié** : `PaymentGatewayService` est un stub — `initiate()` lève toujours `LogicException`, `confirmFromWebhook`/`verifyWebhookSignature` non référencés, aucune route webhook paiement (`app/Services/PaymentGatewayService.php:61-96`) ; `AdminPaymentService::deleteDiscountCode:187-190` jamais appelé (AdminController fait `->delete()` directement :334) ; `NotificationContentService::whatsappText:74-80` sans usage ; relations User jamais utilisées (`User.php:94-111,667-671` — `chatThreads()` retourne même un Builder, pas une relation) ; accesseurs/relations Listing morts (`Listing.php:158-293` : breadcrumb, url, sellerUrl, packItems…) ; vues `resources/views/mails/notifications/telegram.blade.php` + `whatsapp.blade.php` jamais rendues.
- **Complexité** : `ListingSearchService::executeSearch` ~250 lignes (8 blocs de filtres + tri + bornes + facettes) ; méthodes > 80 lignes : `PaymentController::store:59-143`, `ProfileController::update:131-216`, `ListingManagerController::store:44-108` et `performUpdate:125-204`, `AdminDashboardService::getUsersList:18-141`.
- **Anti-patterns** : `catch (\Throwable)` qui avale tout et bascule silencieusement (`OrderService.php:118-122`, `ListingSearchService.php:290-292`, `ThumbnailService.php:57-59`) ; `catch (QueryException)` interprété à tort comme « doublon » (`AdminController.php:314-318`) ; `env()` appelé à runtime (`Listing.php:164`, `SubscriptionService.php:99` — retourne null après `config:cache`, bombe latente déjà documentée) ; champs factices envoyés à l'UI admin (`'last_ip' => null, 'active_sessions' => 0`, `AdminDashboardService.php:111-112,187-188`).

Les registres `ListingQueryService::SELLER_STATUSES/ADMIN_FILTERS:22-35` couvrent partiellement. → Créer `ListingStatus`, `OrderStatus`, `PaymentStatus` (enums) avec transitions explicites.

**Dette technique estimée : moyenne et bien cartographiée** (la roadmap « Tier code » du 03/09 reprend exactement les bons items). Le code est commenté en français, homogène, stylé par Pint en CI.

## 3. Backend Laravel

### 3.1 Bug runtime réel (nouveau, à corriger immédiatement)

- **[CRITIQUE]** `AdminController.php:273` — `throw ValidationException::withMessages(...)` sans `use Illuminate\Validation\ValidationException;` (imports vérifiés lignes 5-34). Dès qu'un admin décoche tous les moyens de paiement dans les settings → `Error: Class "App\Http\Controllers\Api\ValidationException" not found` (500) au lieu d'une 422 propre. Correction : ajouter l'import.

### 3.2 Routes & validation

- **[CRITIQUE]** `GET /api/listings` (public) sans throttle **et** `limit` non borné : `ListingSearchService.php:174-175` passe `$request->integer('limit', 12)` tel quel à `paginate()`. Comparer `OrderController.php:28` (`min(max(...,1),50)`) et `BookCatalogueService.php:38` (cap 12). DoS économique trivial sur une requête multi-`whereRaw`. Correction : cap ≤ 50 + `throttle:catalogue`.
- Le limiter `catalogue` est un **no-op** : `AppServiceProvider::boot` retourne `Limit::none()` quand `config('livrezone.anti_scraping.enabled')` est false, et `ANTI_SCRAPING_ENABLED=false` en prod. Le `throttle:catalogue` de `routes/api.php:130-136` ne protège donc rien.
- `POST /auth/reset-password` sans `throttle:auth` (`routes/api.php:57`) alors que login/forgot-password l'ont (l.53/56) → brute-force du token possible (risque faible : token 64 caractères hashé, mais gratuit à ajouter).
- `level_id`/`subject_id` validés `integer` sans `exists:` (`ListingUpsertRequest.php:27-28`) — compensé en runtime par `ListingProcessorService.php:24-39`, mais incohérent avec `category_id`/`language_id`.
- `status` de `GET /orders` non validé (`OrderController.php:40` → `OrderService.php:264-266`) : `Rule::in([...])`.
- Validation inline résiduelle (déjà en roadmap) : `OrderController.php:63-71,95-102`, `PaymentController.php:33-37,65-70`, `DashboardController.php:25-31,47-51,65-67,152-156`, `NotificationController.php:24-27,107-111`, `LibraryController.php:20-26`.

### 3.3 Transactions manquantes (écritures critiques non atomiques)

- `ChatController::sendMessage:153-161` — create message + update thread + 2× `resetDeletedFor` = 4 écritures sans `DB::transaction`.
- `PaymentController::store:99-118` — delete en masse des paiements `pending` **puis** create puis update code Fatourati, sans transaction : si le create échoue, l'historique pending est perdu.
- `NotificationController::clearBadges:155-173` et `bulk:115-136` — deux tables mises à jour sans transaction.
- `AdminController::updateUserStatus:64-84` — user + mass update listings sans transaction.
- `AuthController:34-43` / `SocialAuthController:143-154` — création User + Profile sans transaction.
- `WishlistController::merge:93-98` — inserts en boucle sans transaction (alors que `CartController::merge:148-181` fait transaction + lockForUpdate : à aligner).
- **Positif** : `OrderService::createOrder:381-425` (transaction + lockForUpdate), `AdminPaymentService::markPaid:121-140`, `NotificationSettingsService::save:47-93`, `AdminController::storeHero:393-410`.

### 3.4 Modèles & N+1

- `User::getNameAttribute` → `$this->profile?->nickname` (`User.php:116-119`) : lazy-load à chaque sérialisation d'un User sans `profile` chargé (jobs, réponses auth). Idem `toSearchableArray` (`Listing.php:36`, `Order.php:42-43`) pendant l'indexation Scout de masse (cf. §5/§7).
- `$fillable` de `Listing` trop large (`status`, `user_id`, `reviewed_by`, `moderation_note`, `deleted_at` : `Listing.php:60-89`) et `DiscountCode::$times_used` fillable — risque latent de mass assignment si un `update($all())` est introduit un jour.
- `Profile::boot` : boucle `while(exists())` en hook `saving` pour l'unicité nickname (`Profile.php:469-474`) — course possible, rattrapée par l'index unique en DB mais avec un 500 au lieu d'un retry.
- **Positif** : `is_admin` hors fillable (fix 26/08 confirmé en place, attributs `#[Fillable]`/`#[Hidden]` Laravel 13 sur User), casts complets et cohérents partout.

### 3.5 Policies & autorisation

- `ListingPolicy`, `ChatThreadPolicy`, `ChatMessagePolicy` présentes et réellement utilisées (y compris dans `routes/channels.php:8-11` pour le broadcast chat). Les endpoints par id (notifications, orders, cart, wishlist) vérifient l'appartenance inline — fonctionnel mais incohérent : créer `OrderPolicy` serait le naturel suivant.
- `RatingService:18-31` : **tout utilisateur authentifié peut noter n'importe quel vendeur, sans achat vérifié, et re-noter à l'infini** (`updateOrCreate`). Voir §10.

### 3.6 Jobs / events / index Meilisearch désynchronisé (nouveau, IMPORTANT)

- Les mass updates de statuts contournent les model events : `AdminController::updateUserStatus:69-79`, `bulkListingStatus:183`, `ListingQueryService::bulkUpdateForSeller:103-106` (bulk-discount/dashboard). Conséquences : **pas de resync Scout/Meilisearch des `listings`** (l'index public `/annonces` diverge jusqu'au `scout:import`… qui n'est d'ailleurs planifié que pour `Profile`, pas pour `Listing`, cf. `routes/console.php`), et **pas de notifications demandeurs** dans le cas `updateUserStatus` (alors que `bulkListingStatus:185-187` les dispatche).
- `MessageSent/Updated/Deleted` en `ShouldBroadcastNow` (synchrone dans le cycle requête chat, `Events/MessageSent.php:12`) — acceptable aujourd'hui, à passer en `ShouldBroadcast` + queue si latence constatée.
- Jobs sans `$tries`/`$backoff`/`$timeout` (`ProcessBookOrderNotifications`, `NotifyDemandersOnListingPublished`) et worker cron sans `--tries` → 1 essai, tout blip réseau va direct en `failed_jobs`.
- **Positif** : mailables et `BookOrderedNotification` en `ShouldQueue`, email paiement envoyé après commit (`AdminPaymentService.php:142-150`), digest chat anti-doublon (`SendChatDigests.php:60-79`).

- **A11y** : non systématiquement vérifiable statiquement, mais aucune remontée bloquante ; RTL géré pour les messages hero arabe.
- **Zéro test frontend** (pas de vitest/jest/playwright dans package.json ; CI = lint + tsc uniquement).

### Important

- **`trustProxies` non configuré** (`bootstrap/app.php` complet vérifié : absent) : derrière Cloudflare → Caddy, `$request->ip()` est l'IP du proxy. Impact double : le limiter `auth` clé par `email|ip` fonctionne (choix documenté `AppServiceProvider`), mais toute future limite par IP bridait tout le monde, et les logs d'activité (`TrackActivity`) enregistrent l'IP proxy. Correctif : `$middleware->trustProxies(at: '*')` ou liste Cloudflare/Caddy (déjà en roadmap « Tier code », décision propriétaire).
- **Tokens Sanctum sans expiration** : `SANCTUM_TOKEN_EXPIRATION` absent du `.env` → `config/sanctum.php:53` = null. Atténué par le fait que le front utilise la session cookie (pas de token localStorage), mais toute token issuance future n'expirerait jamais.
- **5 fichiers `.env.bak*` à la racine** avec creds SMTP/DB en clair (dont un de 166 Ko anormal) + `populate-authors-list-ephemere.php` qui référence des chemins absolus. `.aws.txt` a bien été supprimé de la racine du bind mount (vérifié absent — item roadmap SES clos côté fichier ; la rotation des creds reste à faire).
- **OAuth stateless sans validation de state** (`SocialAuthController::redirect/callback` : `Socialite::driver($provider)->stateless()`)` : pas de vérification anti-CSRF du paramètre `state` → login CSRF (loguer une victime sur un compte attaquant) possible. Risque modéré, correctif : passer par le flow avec session state ou vérifier le state manuellement.
- **`updatePassword`** : OK — `current_password` vérifié via règle `current_password` quand le compte a un mot de passe (`UpdatePasswordRequest.php:20-24`). **reset-password** : tokens hashés par le broker Password, expiration standard — OK.
- **Uploads** : sûrs par conception — ré-encodage Intervention → WebP avec nom aléatoire `Str::random(20).'.webp'` (`ImageUploadService.php:23-44`), aucun input utilisateur dans le chemin, fichier non exécutable. Bon point structurel.
- **Webhook Telegram** : secret `X-Telegram-Bot-Api-Secret-Token` vérifié avec `hash_equals` (`TelegramWebhookController.php:19-23`) — fix S1 de l'audit 25/08 confirmé. La liaison utilise un token à durée limitée à usage unique. **CORS** : durci correctement (`config/cors.php` — origines explicites, rejet de `*` avec credentials). **Session** : `SESSION_SECURE_COOKIE=true`, `http_only`, `SESSION_SAME_SITE=none` (nécessaire au SPA multi-sous-domaine, domain réduit à `.livrezone.com`).

### XSS / injection

- Aucune injection SQL trouvée : tous les `whereRaw`/`orderByRaw` (COALESCE, LOWER(TRIM)) utilisent des bindings `?`. Pas d'`orderBy` construit depuis la requête utilisateur sans whitelist.

## 7. Performance

### Critique
1. **Sitemap sans chunk** (§5.2) : OOM/DoS à la première vraie vague de listings.
2. **Pas de cache de config/routes en prod** : le déploiement (`lz`) ne fait qu'`optimize:clear` ; `bootstrap/cache/` ne contient ni `config.php` ni `routes-v7.php` → chaque requête re-parse 300+ fichiers de config et le fichier de routes. `php artisan optimize` après deploy ( rollback : `config:clear`).

### Important
3. Requêtes non indexables dans le hot path public (§5.3/5.4 : COALESCE prix, MIN/MAX par requête, LOWER(TRIM)).
4. `processExpirations` quotidien (03:00) : full-load + N+1 (`SubscriptionService.php:489-513`) ; `ProcessBookOrderNotifications:241-243` charge tous les vendeurs notifiables à chaque demande publiée ; `NotifyDemandersOnListingPublished` envoie du Telegram synchrone en boucle (10 s timeout × jusqu'à 100 demandeurs) sans timeout de job.
5. `ListingObserver::saved` fait count + save + sync Meili **synchroniquement** dans la requête (`ListingObserver.php:37-53`).
6. Bornes de prix MIN/MAX full-scan à chaque recherche non-compacte (`ListingSearchService.php:195-204`).

## 10. Analyse métier

1. **Contournement de la modération** : `DashboardController::updateInline:41-56` permet au vendeur de changer titre/prix d'une annonce `published` sans passer par `determineStatus()` (contrairement à `performUpdate`, `ListingManagerController.php:136-163`). Un vendeur peut donc republier un contenu modifié sans re-modération. → appliquer la même règle de statut.
2. **Notes sans achat vérifié** (`RatingService:18-31`) : n'importe quel compte peut noter n'importe quelle librairie à l'infini (`updateOrCreate`), ce qui fausse la métrique publique `rating_average` affichée dans l'annuaire. → exiger une commande livrée ou limiter à une note par couple.
3. **Doublons de demandes** : `OrderService::createOrder` protège via `lockForUpdate` + check mais rien au niveau schéma (pas d'index unique sur `(user_id, book_id)` actif) — fragile selon l'isolation MariaDB.
4. **Compteurs/façettes mensongers après actions en masse** : `profiles.listing_count` (affiché publiquement dans l'annuaire) et les facettes ville Meili divergent après bulk-status/bulk-discount/changement de ville (§3.6, §5.7) → incohérences visibles par les visiteurs.
5. **`applyVisibility()` filtre après pagination** (dette connue 04/09) : compteurs/facettes faux pour les demandes masquées (Pro, < 4 h).
6. **Cohérence comptable codes promo** : `AdminPaymentService::markPaid:328-331` incrémente `times_used` par lookup string ; un code supprimé (hard delete `AdminController:334`) rend l'incrément silencieux ; un code recréé hérite d'un compteur gonflé. → soft-delete ou FK `discount_code_id`.
7. **Chat** : `ChatController::store` renvoie 201 même quand le fil existait déjà (`wasRecentlyCreated` non testé, l.88-99) — mineur mais trompeur pour le client.
8. **Quantité jamais décrémentée à la vente** (seul `status='sold'` est posé) : cohérent avec la décision « quantité forcée à 1 », à garder en tête si des packs multi-exemplaires reviennent (la mécanique `listing_pack_items` existe mais est morte, cf. §2).
9. **i18n** : messages utilisateur en français codés en dur (~60 chaînes, 1 seul `__()` dans le code) — assumable en FR-only, mais à trancher explicitement.
10. **Positif** : parcours auth complet et solide (vérification email signée, consentement CGV pré-création, reset broker, désactivation compte → annonces `hidden`), anti-doublon digest, paiement simulateur correctement 403 en prod (`PAYMENT_SIMULATOR=false` vérifié).
