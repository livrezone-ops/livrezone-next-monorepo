## 🧪 CI — FAUX ÉCHECS PHPUNIT SUR SCOUT (02/09 soir — corrigé)

**Constat** : run CI GitHub Actions (`logs_91283083289.zip`, 02/09 21 h) — job
`Backend (pint + phpunit)` rouge : pint PASS (235 fichiers), mais PHPUnit
**81/84 (3 échecs)**, tous dans `tests/Unit/ProfileSearchableObserverTest.php`
(lignes 71, 95, 113) : `Failed asserting that an array contains 1.` Job front
`Frontend (lint + tsc)` vert (0 erreur ; 27 warnings `no-unused-vars` /
`exhaustive-deps` non bloquants).

**Cause racine** : le test mocke l'engine Scout via
`app(EngineManager::class)->extend('meilisearch', ...)` sans jamais forcer le
driver Scout. Il ne passait qu'en local car le `.env` (non versionné) contient
`SCOUT_DRIVER=meilisearch`. En CI, sans `.env`, Scout v11.5.0 retombe sur son
défaut `env('SCOUT_DRIVER', 'collection')` → l'engine **collection** (no-op sur
`update()`/`delete()`) est résolu au lieu du mock → `$indexed`/`$removed`
restent vides. Les 2 autres tests de la classe passaient « par accident »
(ils n'affirment que des tableaux vides).

**Fix** (`tests/Unit/ProfileSearchableObserverTest.php`, `setUp()`) — test
rendu hermétique, indépendant du `.env` :

```php
config([
    'scout.driver' => 'meilisearch',
    'scout.queue' => false,
]);
app(EngineManager::class)->extend('meilisearch', fn () => $engine);
```

**Validation en conditions CI exactes** (Docker PHP 8.5.10 + `SCOUT_DRIVER=collection`
+ `APP_KEY` du workflow, cf. `ci.yml`) :

| Scénario | Résultat |
|---|---|
| Test original sans fix | ❌ 3 échecs reproduits à l'identique (lignes 71/95/113) |
| Avec fix — classe seule | ✅ 5/5 tests, 13 assertions |
| Avec fix — suite complète | ✅ **84/84 tests, 257 assertions** |

⚠️ Le zip de logs CI contient l'`APP_KEY` de test en clair (étape PHPUnit) — ne
pas committer ce zip dans le dépôt.


## 🚨 INCIDENT 02/09 SOIR — SURCHARGE SYSTÈME + MIGRATION CODE-SERVER → OPENVSCODE (résolu)

**Contexte** : migration code-server (rootless) → **openvscode-server**
(`mon-openvscode-server:v2`) le 02/09 ~16 h 56 — à cette occasion le serveur
**Reverb a été extrait dans un conteneur dédié** `reverb` (image
`shinsenter/php:8.5-fpm`, créé 2026-09-02T16:56:57Z, `6060 → 127.0.0.1:6060`).
La suppression de code-server n'était **pas** la cause des plantages
récurrents (cf. leçons ci-dessous).

**Incident** : surcharge mémoire générale (load 31, RAM 8,5/11,8 Go, swap
976/976 Mo plein, thrash ~2 400 Ko/s) → daemon Docker rootless figé → le cron
`/etc/cron.d/lz-schedule` (2 `docker exec`/min **sans flock**) a empilé
**112 processus artisan** bloqués → API en 502 (EOF / connection reset vers
apache `127.0.0.1:32774`) ; processus Reverb en état D depuis 5 h 25 ; accès
fichiers IDE/agent transitoirement coupés (EACCES).

**Correctifs appliqués** (avec le propriétaire) :
- `sudo systemctl restart user@1001.service` → daemon rootless + 7 conteneurs
  redémarrés (livrezone-redis, meilisearch, mariadb, php-fpm-8.5, apache,
  reverb, openvscode-server) ; swap vidé ; load normalisé (1,26 au 03/09 00 h 48).
- **flock ajouté aux 2 lignes du cron** (`/tmp/lz-schedule.lock`,
  `/tmp/lz-queue.lock`) — correctif structurel : l'empilement de processus ne
  peut plus se reproduire.
- Caddy `api-next.livrezone.com.conf` : `handle /app/* { reverse_proxy
  127.0.0.1:6060 }` déplacé **avant** `coraza_waf` → les sockets WebSocket ne
  passent plus par le WAF (amélioration conservée).

**Vérification finale des services (03/09 00 h 48, par l'agent) — TOUS
OPÉRATIONNELS** :

| Service | Test | Résultat |
|---|---|---|
| Redis (`livrezone-redis`) | `redis-cli ping` | ✅ `PONG` |
| Meilisearch (`192.168.1.202:7700`) | `GET /health` | ✅ `{"status":"available"}` |
| Reverb (conteneur dédié) | handshake WS `--http1.1` | ✅ **101** direct · **101** via Caddy · **101** via Cloudflare public |

**Le « HTTP 500 » sur `/app/*` : artefact de test, pas un bug.** Un `curl` nu
négocie **HTTP/2** avec Caddy/Cloudflare ; en h2 les en-têtes
`Connection: Upgrade` / `Upgrade: websocket` sont interdits (RFC 9113) et
abandonnés silencieusement → Reverb reçoit un GET nu → « 500 Internal server
error. » (22 octets). Les vrais clients (navigateurs, Laravel Echo) passent
en HTTP/1.1 → **101 partout**. → Tester les WS avec `curl --http1.1`.

**Leçons** :
1. Ne jamais laisser de non-`.conf` dans `/etc/openpanel/caddy/domains/` :
   la wildcard `import …/domains/*` charge tout — un `.bak` y a causé
   « ambiguous site definition: https://api-next.livrezone.com » au reload
   (backup déplacé hors du dossier).
2. Plantages récurrents antérieurs : l'amplificateur (cron sans flock) est
   corrigé ; déclencheurs à surveiller → swap élargi (4 Go), `MEILI_MAX_MEMORY`,
   ClamAV (~700 Mo résidents) en scan à la demande, pression générale du
   stack rootless (slirp4netns) sur 11,8 Go.
3. Le conteneur `reverb` dédié est sain — aucune reconstruction nécessaire
   (suppression/refonte écartée, preuve : 101 direct).
